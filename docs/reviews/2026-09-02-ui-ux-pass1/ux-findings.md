# UX review — pass 1 (desktop, 1440×900; spot-checked 1280×800 and dark)

Reviewer lens: how the app works for the daily user (jobs, IA, finance wording, feedback/states, interaction cost, over-generation, spec drift, basic a11y). Visual/aesthetic items left to the UI reviewer.

Screenshots: `/private/tmp/claude-502/-Users-dogkan-sarac-Documents-projects-personal-portfolio-tracker/e1e8d7fe-eab2-4c27-b59d-b33a4cb35679/scratchpad/review/shots/ux/` (referred to below as `shots/ux/`). Repo paths are relative to `/Users/dogkan.sarac/Documents/projects/personal/portfolio-tracker/`.

Method note: every route in the brief was driven with Playwright (scripts `ux01`–`ux13` in `<scratchpad>/pw/`); dialogs were opened and cancelled, nothing was saved. Dashboard vs Portfolio totals were compared in two tabs loaded simultaneously — they agreed to the cent ($47,896.23 / P&L $3,957.70 on both), so the historical "two totals" sore spot is NOT reproduced (earlier per-run differences were live price drift between loads).

### UX-01 · high · Add Transaction dialog — the primary actions are clipped below the dialog's visible edge for Buy/Sell/Dividend/Interest at 1440×900
- Evidence: `shots/ux/11-add-buy-1440.png` (no Cancel/Save/Add visible; dialog ends under the Notes box) vs `shots/ux/07-add-type-Withdrawal.png` (shorter form — footer visible). Measured: dialog `max-height: 810px`, `overflow-y: auto`, content `scrollHeight` 863 (Buy) / 885 (Dividend) / 887 (Buy prefilled from an asset page); submit button top = 860px while the dialog's bottom edge = 855px. At 1280×800 the button sits 95px below the edge. `src/components/transactions/AddTransactionModal.tsx:955-985` (footer rendered inside the scrolling `DialogContent`), `:449-458` (`canSubmit`).
- Why it matters: "record the trade I just made" is the #3 daily job and Buy is its default type — on a normal laptop the user fills the form and sees no way to submit; the dialog scrolls but shows no cue (no visible scrollbar, no cut-off hint), so the discovery is by accident.
- Proposed change: keep the footer out of the scroll region (sticky footer inside `DialogContent`, header + body scroll), or shorten the Buy form (Fee and its currency inline with Unit Price, Notes collapsed until clicked). Verify the submit button's bounding box is inside the dialog at 1280×800 for every type.

### UX-02 · high · Display currency = TRY: Portfolio and Asset Detail keep P&L and cost in USD while Value is in TRY — the Dashboard converts P&L to TRY
- Evidence: `shots/ux/08-portfolio-TRY.png` (summary bar "Total Portfolio Value ₺2.309.025,44" beside "P&L $3,959.10"; every row "Value ₺…" beside "P&L −$654.12"); `shots/ux/10-asset-AAPL-TRY.png` ("Value ₺148.851,38", "Total return $627.73", "Today $541.45"); `shots/ux/08-dash-TRY.png` ("Total ₺190.858,54 · Invested ₺2.118.166,89"). Code: `src/components/portfolio/PortfolioSummaryBar.tsx:74` (`formatSignedCurrency(totalPnlUsd, "USD")`), `src/components/portfolio/PortfolioRow.tsx:193,202-203`, `src/components/portfolio/PortfolioGroupHeader.tsx:63`, `src/components/asset-detail/AssetPositionSummary.tsx:52,84,173`, `src/components/asset-detail/AssetPlatformTable.tsx:65-72` — all hardcode `"USD"`; `src/components/dashboard/DashboardHero.tsx:588-596,649-656` convert via `totalPnlTry`/`investedNowTry`. Spec: `docs/components/11-settings-data-portability.md:27-30` ("re-denominates every money amount across the whole app immediately").
- Why it matters: a TRY-mode reader of the Portfolio table sees two currencies in one row with no marker, and the same P&L figure is ₺ on one page and $ on the next — the exact "different definition across pages" failure the brief names.
- Proposed change: pick one rule and apply it app-wide. My recommendation: presentation follows the display currency everywhere (convert P&L/cost at the live rate like the hero does — the USD anchor is a computation rule, not a display rule), and update spec 08/12 to say so. If the owner prefers USD-anchored P&L to stay visibly USD, then the hero must stop converting and the P&L column header should read "P&L ($)" in TRY mode.

### UX-03 · medium · Portfolio — Total/Daily, Platform/Category, sort and search reset on every route change, while the dashboard hero remembers mode/range/measure across a reload
- Evidence: `shots/ux/08-portfolio-daily-platform-before-nav.png` (Daily + Platform selected) → Dashboard → Portfolio → `shots/ux/08-portfolio-after-nav.png` (back to Total + Category; pressed states read `["Total","Category"]`). `src/hooks/usePortfolio.ts:135-138` (plain `useState` defaults). Dashboard: `src/components/dashboard/DashboardHero.tsx:194-209` keeps viewMode / timeRange / benchmark / measure in `usePersistedState` (`src/hooks/usePersistedState.ts`, localStorage) — after a reload the hero still showed Performance · MWR · 1Y (`ux02` log "AFTER RELOAD"). Spec `docs/components/08-portfolio-page.md` Contract: "UI state held during the session … (none persisted across reloads)" — a route change is within the session.
- Why it matters: the owner who prefers "Today" or the platform grouping re-clicks two toggles on every visit (job: "what moved?" then "check one position" and back), and the two most-used pages disagree on whether the app remembers the reader's choice.
- Proposed change: persist `returnMode`, `groupBy`, `sortBy` the same way the hero persists its view (same storage, same lifetime); keep the search box ephemeral. Spec 08 should then state the persistence explicitly.

### UX-04 · medium · Dashboard hero, Value mode, ALL/2Y — the period delta equals the entire portfolio value and is coloured as a gain ("$47,481.31 all time")
- Evidence: `shots/ux/02-dash-value-ALL.png` (green "$47,481.31 all time" under the "$47,481.31" headline; same on 2Y). `src/components/dashboard/DashboardHero.tsx:556-566` (amount always rendered; only the % is suppressed when there is no base). Spec `docs/components/07-dashboard.md` "Percent denominator rules" hides the percent for a ~$0 start but says nothing about the amount.
- Why it matters: the biggest green number on the landing page reads as "+$47K profit all time" when the real lifetime Total P&L is $3.5K one line below; a synthetic-zero anchor produces a Δ that is deposits, not gain.
- Proposed change: when the window has no real starting base (the same condition that hides the %), hide the Δ amount too or render it neutral with the wording "since first deposit"; the lifetime P&L stays in the Performance subtitle. Extend the spec rule to cover the amount.

### UX-05 · medium · Dashboard hero labels the same figure "Cost basis" in Value mode and "Invested" in Performance mode; per the glossary it is neither exactly
- Evidence: `shots/ux/02-dash-value-YTD.png` ("Cost basis $43,938.53") vs `shots/ux/01-dashboard.png` ("Invested $43,938.53"). `src/components/dashboard/DashboardHero.tsx:262-263` (`investedNowUsd = currentValueUsd - totalPnlUsdNow`), `:571-573` ("Cost basis"), `:649` ("Invested"), `:741` (tooltip series "Cost basis"). Glossary: `docs/components/GLOSSARY.md` "Net invested capital" (value − P&L) vs "FIFO lots and cost basis" (USD cost of remaining lots) are different terms; the Portfolio "Bought" column and Asset Detail "Cost Basis" show the FIFO figure.
- Why it matters: the reader compares "Cost basis $43,938" on the dashboard with "Cost Basis $2,459.98" per asset and cannot reconcile them; wording precision is a stated standard for this app.
- Proposed change: label it "Net invested" in both modes and in the chart legend/tooltip (glossary term), and keep "Cost basis" for FIFO figures only.

### UX-06 · medium · The money-weighted % wears three different labels across pages — and none on Asset Detail, where it sits next to a differently-based %
- Evidence: hero "XIRR 7.9%/yr" (`src/components/dashboard/DashboardHero.tsx:102-105`), Portfolio bar "MWR 13.55%" (`src/components/portfolio/PortfolioSummaryBar.tsx:14-18`), Asset Detail "Total return $634.81 (60.85%) ≈35.97%/yr" with no label or hover hint (`src/components/asset-detail/AssetPositionSummary.tsx:50-63`; `shots/ux/05-asset-AAPL.png`), right beside "Unrealized P&L $634.82 (25.81%)". Glossary defines one term: "Money-Weighted Return (MWR / XIRR)".
- Why it matters: the same dollar figure ($634.8) carries 60.85% and 25.81% in adjacent cards; without a label the reader has to know one is money-weighted and the other is over cost. The app's own rule (memory + spec 13 "one term per concept") is being broken by its two most-read figures.
- Proposed change: one micro-label app-wide (e.g. "MWR", since the % shown is cumulative MWR; keep "/yr" only on annualised readings) with one shared hint string; add it to Asset Detail's Total return %, and consider a "on cost" hint on the unrealized %.

### UX-07 · medium · Recording an internal transfer — the form has no "Transfer" type; the user must choose "Withdrawal" and then notice a "Destination Platform" field, although the log and the filter call the result "Transfer"
- Evidence: `shots/ux/07-add-type-Withdrawal.png` (type row: Buy · Sell · Deposit · Withdrawal · Dividend · Interest · Fee · Tax; "Source Platform / Destination Platform" appear under Withdrawal); `shots/ux/09-tx-transfer-filter.png` (log row and chip say "Transfer"). Spec `docs/components/04-transaction-system.md` UI contract "`transfer_out`: a destination platform"; glossary display labels reserve "Transfer" for the linked pair.
- Why it matters: moving BTC from Midas Kripto to Paribu is a routine job; a user scanning the type row for "Transfer" concludes it is not supported, or records a Withdrawal + Deposit pair by hand (which then books external flows and distorts net invested).
- Proposed change: add a "Transfer" type button that sets `transfer_out` with the destination selector required (Withdrawal keeps destination optional/hidden), or at minimum add helper text under Withdrawal: "Pick a destination to record a transfer between your platforms".

### UX-08 · medium · Add form defaults force two avoidable choices on every trade: Platform is not prefilled when the asset is held on exactly one platform, and Funding source defaults to "External cash" although the seeded broker trades are all platform-funded
- Evidence: `shots/ux/08-portfolio-row-plus-modal.png` and `shots/ux/05-asset-AAPL-record.png` (AAPL prefilled, "Total balance: 9.502 AAPL", yet "Platform: Select platform…" — AAPL is only held on IBKR); `shots/ux/09-add-buy-AAPL-IBKR.png` + `shots/ux/09-add-funding-options.png` (after choosing IBKR the funding stays "External cash (no deduction)" while "IBKR — 2,771 USD" is available); the edit dialog of a real buy shows "Funding source: IBKR — USD" (`ux07` log). `src/components/transactions/AddTransactionModal.tsx:200` (`setPlatformId(modalState.prefilledPlatformId ?? "")`), `:106` (`fundingSource` starts `null` = external), `:319-339` (funding only follows a platform change if already set).
- Why it matters: 2 extra clicks per trade, and the funding default is the risky one — forgetting it silently records external money and inflates net invested capital (the number every % is judged against).
- Proposed change: when the asset has holdings on exactly one platform, prefill it (row "+" and asset-page button can pass it); when a Buy's platform has a price-currency cash holding whose balance covers the total, default funding to it and fall back to external otherwise (keep the explicit "External cash" option).

### UX-09 · medium · Retirement — chart and milestones show negative portfolio values (−$832K at 85, −$2.16M at 90; y-axis down to −$20M)
- Evidence: `shots/ux/06-retirement-q-What.png` (table rows 85/90 pessimistic negative; chart axis −$20M); `src/lib/retirement/projection.ts:167-168` ("The drawdown is not floored at zero: a plan that overspends ends negative rather than silently solvent"). Spec `docs/components/13-retirement-planning.md` describes depletion as "spent to zero" and preservation as "typically keeps rising"; the glossary never defines a negative portfolio.
- Why it matters: a portfolio cannot be −$2M; the reader has to translate the sign into "ran out around 80", which is the actual answer the table should give.
- Proposed change: keep the unfloored maths internal for the solvers, but floor displayed series/tables at 0 and print "depleted at age N" in the pessimistic cell/tooltip and as a chart marker. Add this to spec 13.

### UX-10 · medium · Mixed Turkish/English — the dashboard hero axis and tooltips are hardcoded to `tr-TR` in an otherwise English UI ("Ağu 2026", "Şimdi", "19 Ağustos 2026")
- Evidence: `shots/ux/02-dash-value-YTD.png` (x-axis "Oca 2026 … Ağu 2026 · Şimdi"), `shots/ux/13-hero-tooltip.png` (tooltip "19 Ağustos 2026 | You (TWR) …"). `src/components/dashboard/DashboardHero.tsx:396-407` and `:746-755` (`toLocaleDateString("tr-TR", …)`, literal `"Şimdi"`), also `src/hooks/useDashboardHero.ts` and `src/lib/dashboard/intraday.ts` (grep `tr-TR`). Every other date in the app is English ("Aug 28, 2026", "September 2nd, 2026", asset chart "Jun 17"). Note: TRY *number* formatting via `tr-TR` is a deliberate config choice (`src/lib/config.ts:60`) and is not what this finding is about.
- Why it matters: the landing page's chart speaks a different language from the rest of the app, and the tooltip's "Şimdi" row is the one row that carries today's number.
- Proposed change: format hero dates with the same locale the rest of the app uses and replace the "Şimdi" literal with "Now" (single constant), or make the UI locale one app-wide setting.

### UX-11 · medium · Budget — months with several income entries are disabled with "edit them individually", but no surface exists to edit individual entries
- Evidence: `shots/ux/06-budget.png` (Aug, Jun, May, Mar 2026 income cells are not clickable); tooltip text `src/components/budget/MonthlyBudgetTable.tsx:159-162` (`disabled={monthEntries.length > 1}`, "Several income entries this month — edit them individually"); no component or page under `src/components`/`src/pages` reads cash-flow entries individually (grep `CashFlowEntry|cash_flow_entries` returns only the budget hook/table). Spec `docs/components/14-budgeting.md:60` ("its entries are edited individually") describes a surface that isn't built.
- Why it matters: a bonus month is exactly the month the owner wants to correct, and the app tells him to go somewhere that doesn't exist.
- Proposed change: either open the same inline editor listing that month's entries (amount per entry, delete) or, until the expense ledger lands, let the cell edit the month's total by adjusting the last entry. Update spec 14 to match whichever ships.

### UX-12 · low · Transactions summary colours Buy Volume green and Sell Volume red (and quantities by sign) — the gain/loss palette applied to figures that are not gains or losses
- Evidence: `shots/ux/01-transactions.png` ("$15,915.48" green, "$5,544.83" red; "$0.00" buy volume renders green under the Sell filter, `ux04` log). `src/components/transactions/TransactionSummary.tsx:27,38` (`gainLossClass(true)` / `gainLossClass(false)`).
- Why it matters: in this app green/red means "I made / lost money" everywhere else; a sale is not a loss, and a red $6K on the audit page draws the eye to nothing.
- Proposed change: neutral foreground for both volumes (and consider neutral quantity colouring, keeping the ± sign); reserve the palette for the realized P&L line on sell rows.

### UX-13 · low · Campaigns "Refresh" only re-reads the stored research run; placed next to "Data from Aug 27, 2026" it reads as "run research now" and visibly does nothing
- Evidence: `shots/ux/06-campaigns.png` (header "Data from Aug 27, 2026 · Refresh"); `src/pages/CampaignsPage.tsx:156-161` → `src/contexts/CampaignsContext.tsx:36-52` (`fetchLatestCampaigns()` — a DB read, no research trigger). Spec `docs/components/15-campaigns.md` has no manual refresh control (a forced pass is a job-side override).
- Why it matters: the dataset changes weekly by design, so the button never changes anything the user can see; it is an unrequested control that promises fresher data than it delivers (over-generation per CLAUDE.md).
- Proposed change: remove the button (the page already refetches on mount), or if a manual research pass is wanted, wire it to the forced run behind a confirmation and rename it "Run research".

### UX-14 · low · Add Transaction — submit buttons are simply disabled until the form is valid, with no inline validation and no hint about what is missing
- Evidence: `shots/ux/09-add-empty-submit.png`; `src/components/transactions/AddTransactionModal.tsx:449-458` (`canSubmit`), `:967-984` (`disabled={!canSubmit}`, no `title`); `disabled:pointer-events-none` on the button means no tooltip can fire. Only the over-balance case has an inline message (`shots/ux/09-add-sell-overbalance.png`, good).
- Why it matters: combined with UX-01 the user sees neither the button nor a reason; when the button is visible but greyed, a missing Unit Price (or a platform on a Deposit) is guesswork.
- Proposed change: enable the buttons and validate on submit with field-level messages (the pattern the over-balance check already uses), or show a single muted line above the footer naming the first missing field.

### UX-15 · low · Header privacy toggle has no accessible name; the icon-only button announces as "button"
- Evidence: keyboard walk on the dashboard (`ux06` log "DASH TAB PATH": `BUTTON ""` between the Settings link and "Switch to dark mode"); `src/components/layout/Header.tsx:47-63` (Tooltip only, no `aria-label`) vs `src/components/common/ThemeToggle.tsx:22` (has `aria-label`).
- Why it matters: it is the one control the owner reaches for before screen-sharing; keyboard/screen-reader users get no name, and the two sibling icon buttons are built inconsistently.
- Proposed change: `aria-label={obfuscated ? "Show values" : "Hide values"}` on the button, mirroring ThemeToggle.

### UX-16 · low · Settings page does not match its spec: no display preferences (currency / theme / privacy) and no pointer to import; it is three management tabs
- Evidence: `shots/ux/06-settings.png` (tabs Assets · Platforms · Snapshots; subtitle "Manage your platforms, assets, and snapshots"); `src/pages/SettingsPage.tsx:16-34`. Spec `docs/components/11-settings-data-portability.md` UI contract: "Preferences — a control to pick display currency … theme … value-privacy toggle … Import — surfaced via Component 4 … pointer".
- Why it matters: the header already carries all three toggles, so the user is not blocked — but the spec is the rebuild contract and currently describes a page that doesn't exist; either the page or the doc is wrong.
- Proposed change: amend spec 11 to say preferences live in the global header only (my preference — no duplicate controls), and add a one-line "Import transactions → Bulk add" link under a small "Data" heading if the import pointer is still wanted.
